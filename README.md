# Telegram-бот мониторинга корпоративных событий

36 базовых активов, единый реестр источников и дешёвый конвейер: источники опрашиваются один раз, публикации сопоставляются активам локально, LLM (Gemini 2.5 Flash) получает только короткие батчи кандидатов.

## Архитектура

```text
Источники (RSS/SEC → HTML → Tavily раз в сутки)
  ↓  параллельный опрос, каждый источник один раз
Публикации
  ↓  локальная фильтрация: дубли URL/заголовков, старые, кэш processed_articles,
  ↓  ключевые слова корпоративных событий, сопоставление активам по имени/алиасам
Кандидаты
  ↓  батчи по 20 → Gemini 2.5 Flash (только классификация, JSON)
События → SQLite (дедупликация по fingerprint) → Telegram (краткое + полное уведомление)
```

1. Планировщик раз в N минут опрашивает источники с истёкшим `refresh_interval` (`/scan` — все сразу).
2. Каскад: официальные RSS/SEC-фиды → HTML-страницы IR без фидов → резервный поиск Tavily не чаще раза в сутки (или `/fullscan`).
3. Модель данных: базовый актив (+ алиасы и контрактные коды как идентификаторы) ← подписки → единый реестр источников; публикации кэшируются, события дедуплицируются.
4. Все обращения к модели — через интерфейс `LLMProvider` (`app/llm.py`); смена модели = новый провайдер + `.env`.
5. Оформление сообщений — только локально (`app/formatters.py`), LLM тексты не оформляет.
6. Временные ошибки сети/API (429 и 5xx) повторяются с экспоненциальной задержкой; недоставленные события досылаются при следующей проверке.
7. JSON-файлы в `data/` — только начальная загрузка: при первом запуске всё импортируется в SQLite, дальше активы и источники живут только в базе и редактируются через Telegram.
   Дополнительно при каждом старте выполняется синхронизация с `underlyings_sources.md` (рабочая методология): недостающие активы, ISIN, биржи и источники добавляются идемпотентно, существующие данные не перезаписываются и не удаляются.
8. `/cost` показывает стоимость LLM за сегодня/месяц и экономию за счёт кэша.

## 1. Что зарегистрировать

### Telegram
1. Откройте в Telegram `@BotFather`.
2. Отправьте `/newbot`.
3. Задайте название и username, заканчивающийся на `bot`.
4. Скопируйте токен.
5. Напишите созданному боту `/start`.

### Google AI (Gemini)
1. Откройте Google AI Studio (aistudio.google.com).
2. Создайте API key.
3. Запишите его в `.env` как `GOOGLE_API_KEY`.

### Tavily (необязательно)
1. Создайте аккаунт Tavily и API key.
2. Tavily используется только как резервный поиск раз в сутки и в `/fullscan` — бесплатного лимита обычно достаточно. Без ключа этот уровень просто отключается.

### GitHub и Railway
1. Создайте аккаунт GitHub.
2. Создайте аккаунт Railway и подключите GitHub.

## 2. Локальный запуск в VS Code

Откройте папку проекта в VS Code. Затем откройте Terminal → New Terminal.

### macOS / Linux

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

### Windows PowerShell

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
Copy-Item .env.example .env
```

Откройте `.env` и заполните значения:

```env
TELEGRAM_BOT_TOKEN=токен_от_BotFather
ADMIN_TELEGRAM_ID=ваш_числовой_id
GOOGLE_API_KEY=ключ_Google_AI
TAVILY_API_KEY=ключ_Tavily   # необязательно, только для резервного поиска
USER_AGENT=corporate-events-monitor/1.0 (ваш@email)   # нужен для SEC EDGAR
```

Чтобы узнать Telegram ID до запуска основного проекта, можно временно оставить `ADMIN_TELEGRAM_ID=0`, запустить бота, отправить `/id`, затем остановить бот `Ctrl+C`, записать полученное число в `.env` и запустить снова. В этом режиме доступна только команда `/id`, автоматические проверки не планируются.

Проверка синтаксиса:

```bash
python -m compileall app
```

Запуск:

```bash
python -m app.main
```

### Тесты

```bash
pip install -r requirements-dev.txt
python -m pytest
```

Тесты покрывают инициализацию БД, загрузку 36 активов и 234 промптов, идемпотентность импорта, дедупликацию событий, парсинг ответа модели, retry-логику и команды `/add`, `/addsource`, `/interval`.

В Telegram отправьте:

```text
/status
/list
/scan
```

Первая полная проверка может использовать много поисковых запросов. Для первого теста временно оставьте в базе 1–2 актива либо увеличьте интервал.

## 4. Команды Telegram

Система построена вокруг сущности «базовый актив»: код контракта Московской биржи — лишь один из его идентификаторов. Во всех командах, где нужен актив, подойдёт любой известный идентификатор: канонический код, контрактный код (для составных кодов вида `BR, BRM` — каждый по отдельности), тикер, алиас или имя (можно часть имени). При неоднозначном запросе бот покажет кандидатов.

- `/scan` — немедленная полная проверка.
- `/list` — список активов и количество источников.
- `/find ТЕКСТ` — найти актив по любому идентификатору или части имени.
- `/add CODE | TYPE | NAME | АЛИАСЫ` — добавить актив (алиасы через запятую, необязательны).
- `/alias АКТИВ | АЛИАС` — добавить новый идентификатор (тикер, ISIN, альтернативное имя) без изменения кода.
- `/addsource АКТИВ | URL` — добавить официальный источник.
- `/remove АКТИВ` — удалить актив.
- `/interval 60` — проверять раз в 60 минут, минимум 15.
- `/pause` и `/resume` — остановить или возобновить автоматические проверки.
- `/digest` — сводка событий за последние 24 часа с разбивкой по важности.
- `/events` — компактная история последних событий.
- `/event 17` — полный аналитический отчёт о событии №17.
- `/status` — состояние сервиса.

## Формат уведомлений

О новом событии бот присылает краткое уведомление с кнопкой «Подробнее»:

```text
🚨 Дробление акций
SPYF · SPDR S&P 500 ETF Trust
🔴 Критическая

Эмитент объявил дробление паёв в соотношении 1:5.
Количество паёв вырастет впятеро.

⚠️ Проверить необходимость корректировки параметров контракта.

Официальный источник
Подробнее: /event 17
```

Полный отчёт (кнопка «Подробнее» или `/event 17`) содержит базовый актив, код инструмента, тикер, даты события/публикации/вступления в силу, статус подтверждения, важность (🔴 критическая / 🟠 высокая / 🟡 средняя / 🟢 низкая), блоки «Что произошло», «Ключевые параметры», «Возможное влияние», «Рекомендуемое действие», нумерованные источники, достоверность и время обнаружения по МСК. Пустые поля не выводятся; события со статусом «слух» не рассылаются (их видно только в `/debugscan`). Сообщения — HTML с экранированием; при сбое разметки бот автоматически отправляет обычный текст, длинные отчёты режутся на несколько сообщений без разрыва тегов и ссылок.

Сопоставление публикаций с активами — многоуровневое и полностью локальное: точные идентификаторы (ISIN/CUSIP/CIK/LEI, SEC filer) → точные названия → алиасы → fuzzy (только как кандидат) → владение источником. Каждое решение имеет score и объяснение. Управление:

- `/matchtest АКТИВ | ТЕКСТ` — проверить, как заголовок сопоставится с активом.
- `/unmatched [АКТИВ]` — публикации, не прошедшие порог; `/match ID АКТИВ` — привязать вручную; `/ignorepublication ID` — пометить нерелевантной.
- `/setid АКТИВ | cik | 1577552` — добавить точный идентификатор (ISIN/CUSIP/CIK/LEI/тикеры/эмитент); выдуманные значения не подставляются автоматически.
- `/rematch [АКТИВ|all] [дней]` — пересопоставить сохранённые публикации локально, без сети и без LLM (после улучшения правил или роста MATCHER_VERSION).

Перед миграцией схемы база автоматически копируется в `monitor.db.bak-v3` рядом с оригиналом.

### Доступ сотрудников

Роли двухуровневые: администратор (`ADMIN_TELEGRAM_ID`) управляет всем; подписчики получают уведомления о событиях и могут читать `/digest`, `/events`, `/event` и открывать «Подробнее». Остальные команды отвечают подписчикам «Нет доступа».

1. Сотрудник открывает бота и отправляет `/id`.
2. Администратор: `/adduser 123456789 Иван Петров`.
3. Управление: `/users` — список, `/removeuser ID` — отписать.

Диагностика (только для администратора):

- `/debugscan TSM` — поэтапная проверка одного актива: конфигурация → Tavily → Claude (сырой ответ) → фильтрация → запись в базу. В этом режиме модель возвращает события с любым confidence, но в базу записываются только прошедшие рабочий порог.
- `/dbstats` — путь, размер и наполнение SQLite-базы, история запусков сканирования.
- `/testevent TSM` — искусственное событие: запись, отправка, пометка sent_at; повторный вызов должен определить дубликат.

После `/scan` бот присылает статистику: запросов, результатов, материалов для Claude, событий, отклонений, дубликатов, записей и ошибок.

Пример:

```text
/add TSM | ADR | Taiwan Semiconductor Manufacturing ADR | TSMC, 2330.TW
/alias TSM | Тайвань Семикондактор
/addsource TSMC | https://investor.tsmc.com/english
/debugscan 2330.TW
```

При первом запуске новой версии существующая база мигрирует автоматически: алиасы переносятся в таблицу `asset_identifiers`, составные коды разбиваются на отдельные идентификаторы. Миграция одноразовая и идемпотентная.

## 6. Railway

1. Нажмите New Project → Deploy from GitHub Repo.
2. Выберите репозиторий.
3. Railway увидит `Dockerfile` и соберёт worker.
4. Откройте сервис → Variables и добавьте:
   - `TELEGRAM_BOT_TOKEN`
   - `ADMIN_TELEGRAM_ID`
   - `GOOGLE_API_KEY`
   - `TAVILY_API_KEY` (необязательно)
   - `MODEL=gemini-2.5-flash`
   - `SCAN_INTERVAL_MINUTES=60`
   - `DB_PATH=/data/monitor.db`
   - `TIMEZONE=Europe/Amsterdam`
   - `USER_AGENT=corporate-events-monitor/1.0 (ваш@email)`
5. Добавьте Railway Volume и смонтируйте его в `/data`. Без volume SQLite-файл может потеряться при новом деплое.
6. Нажмите Deploy.
7. В Deploy Logs найдите строку `Bot initialized`.
8. Отправьте боту `/status`.

Публичный домен не нужен: бот использует long polling, а не webhook.

## 7. Что проверить перед рабочим использованием

1. Временно оставьте один актив и выполните `/scan`.
2. Проверьте, что сообщение содержит источник и корректный тип события.
3. Повторите `/scan`: то же событие не должно прийти повторно.
4. Добавьте тестовый актив через `/add` и источник через `/addsource`.
5. Перезапустите сервис и убедитесь, что актив сохранился.
6. Проверьте расходы Anthropic и Tavily.

## Ограничения MVP

- Некоторые сайты блокируют автоматическое чтение. Поэтому поиск через Tavily используется как основной транспорт к материалам, а официальные домены получают приоритет.
- Почасовой полный мониторинг 36 активов может быть дорогим. Практичный старт: 2–4 часа, а для наиболее критичных активов позже сделать отдельную частоту.
- Автоматическая оценка не заменяет финальную проверку человеком. В сообщении есть confidence и ссылка на первоисточник.
- SQLite подходит для одного экземпляра бота. При нескольких worker нужно перейти на PostgreSQL и распределённую блокировку.
- У актива `STOX` в исходной методологии нет официальных источников: он ищется без приоритета доменов, пока источник не добавлен через `/addsource STOX | URL`.
